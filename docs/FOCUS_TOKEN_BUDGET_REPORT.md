# Focus 输入 Token 预算实验报告

测试日期：2026-08-21
模型：DeepSeek V4 Flash
模式：关闭思考
接口：DeepSeek 官方 API

## 结论

推荐配置：

```text
FOCUS_PROMPT_TARGET_TOKENS = 8000
FOCUS_PROMPT_MAX_TOKENS = 12000
```

这两个值表示最大预算，不要求短对话补齐到对应长度：

- 输入不足 8000 tokens 时发送全部有效上下文。
- 输入超过 8000 tokens 时开始压缩低优先级背景。
- 输入不得超过 12000 tokens。
- 完整 final 对话仍保存在内存中，预算只约束模型 Prompt 投影。

V4 Flash 的上下文容量约 1M，但模型“能够接收”的长度不等于实时 Focus 的最佳长度。实验中，超过约 12K 后开始稳定丢失位于长上下文前部的动态约束；48K 之后延迟和质量都明显恶化。

## Prompt 格式

System Prompt 固定为 341 个字符，定义：

```text
I = 面试官
C = 候选人
Q = 上一个已提交问题
A = 上次系统推荐回答
```

动态输入使用极简 Markdown：

```markdown
# 上一焦点
Q: Redis 为什么快？
A: Redis 快主要因为内存、单线程、I/O 多路复用和高效数据结构。

# 对话
- C: 我刚才主要回答了内存和单线程。
- I: 那 Redis 的 I/O 模型为什么高效？
```

模型输出为严格 JSON。

## 实验设计

总计执行超过 100 次正式请求，另有每轮连接预热与 Token 校准请求。

统一条件：

- 客户端连接复用。
- 并发为 1，排除网关排队干扰。
- 请求顺序按固定随机种子打乱。
- 使用 API 返回的 `prompt_tokens`，不以字符估算值作为最终数据。
- 关闭思考，温度为 0.1。
- 关键内容分别放在上下文前部 10%、中间 50% 和后部 90%。

覆盖任务：

- 新问题：MySQL 慢查询。
- 新话题：JVM 对象回收。
- 追问：Redis I/O 模型。
- WAIT：背景尚未讲完。
- THINK 路由：带十万 QPS、一致性和容灾约束的分布式限流器。

长上下文由带 I/C 身份的自然 Markdown 对话组成。关键问题后增加“请回答刚才的核心问题”，测试模型是否能够从长上下文中还原完整问题，而不是只复述最新一句。

中文 Markdown 的本轮校准比例约为：

```text
1 token ≈ 1.75 个字符
```

实际实现仍需预留估算误差，并以线上 API usage 持续校准。

## 位置与多任务测试

MySQL 问题放在开头、中间和结尾时，8K～64K 均能找回。但是多约束 THINK 问题暴露了更严格的限制。

五类任务的中间位置测试：

| 实际档位 | 正确率 | 完整响应中位数 | 本轮最大值 |
|---:|---:|---:|---:|
| 约 7.7K | 5/5 | 1.22s | 1.47s |
| 约 15.6K | 5/5 | 1.69s | 2.83s |
| 约 31.1K | 5/5 | 1.36s | 2.40s |
| 约 46.7K | 4/5 | 2.61s | 2.98s |

48K 的失败表现为：模型正确选择 THINK，但把完整问题：

```text
设计一个支持每秒十万请求的分布式限流器，并说明一致性和容灾方案。
```

错误压缩为：

```text
请按刚才的约束完成设计。
```

这会导致后续 THINK 模型收不到关键数字与约束。

## 前置多约束压力测试

将完整系统设计约束放在上下文前 10%，末尾只有“请按刚才约束完成设计”：

| 实际 Prompt Tokens | 重复次数 | 完整还原 |
|---:|---:|---:|
| 7,749 | 5 | 5/5 |
| 11,714 | 5 | 5/5 |
| 12,680 | 5 | 0/5 |
| 13,667 | 5 | 0/5 |
| 15,604 | 5 | 0/5 |

本测试形态下，可靠性在约 12K～13K 之间出现稳定断层。这是注意力和问题还原失败，不是上下文容量不足或接口报错。

## 为什么选择 8K / 12K

8K 作为默认目标：

- 新问题、追问、WAIT、FAST、THINK 全部通过。
- 关键内容位于开头、中间、结尾均通过。
- 前置多约束重复测试 5/5。
- 完整 Focus 结果通常约 1 秒级。
- 对一次 Focus 区间来说已经能容纳大量真实对话。

12K 作为硬上限：

- 前置多约束重复测试 5/5。
- 比 8K 多出约 50% 的弹性空间。
- 下一档约 12.7K 已经稳定失败，因此不应继续放宽。

配置语义：

```text
0～8K：完整发送
8K～12K：按优先级压缩后发送
超过 12K：必须压缩到 12K 内，禁止原样调用
```

## 上下文压缩优先级

必须保留：

1. System Prompt。
2. 上一个 Focus 问题。
3. 最新面试官问题及必要前置语句。
4. 与当前追问有关的候选人实际回答。
5. 数字、代码、复杂度和业务约束。

优先压缩：

1. 重复的普通背景。
2. ASR 噪声和无意义口语。
3. 与当前问题无关的旧陈述。
4. 上一次推荐回答中的次要细节。

不能采用单纯的头部或尾部截断。前置约束实验已经证明，关键内容位于开头时会被长背景稀释。

## 限制

- 背景对话为可复现的合成 Markdown，不等同于所有真实面试分布。
- 多任务集目前为 5 类，需要继续加入真实录音回放。
- 延迟会受网络和服务负载影响，单轮中出现过明显抖动。
- 模型或服务版本变化后必须重新评测。
- 1M 上下文容量尚未做 256K 以上压力测试，因为 128K 已达到 6.36 秒，且不可能进入实时候选方案。
